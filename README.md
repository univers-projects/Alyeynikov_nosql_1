# Music Streaming Analytics Service

Це навчальний проєкт з MongoDB для аналізу датасету Spotify Tracks. Ідея роботи така: спочатку ми завантажуємо CSV у MongoDB майже без змін, а потім перетворюємо плоскі рядки з CSV у зручні документи для аналітики.

У результаті в базі `spotify` є дві основні колекції:

- `tracks_raw` - сирі дані після завантаження з CSV.
- `tracks` - очищена і структурована колекція, з якою виконуються всі запити.

## Як запустити проєкт

Спочатку потрібно створити безкоштовний кластер MongoDB Atlas, додати користувача бази даних і дозволити підключення зі свого IP у Network Access.

Після цього треба створити файл `.env` у корені проєкту:

```env
MONGO_URI=mongodb+srv://user:password@cluster.mongodb.net/
```

Далі встановлюємо Python-залежності:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Перший скрипт завантажує CSV у колекцію `tracks_raw`:

```bash
source .env
python scripts/01_load_data.py
```

Після цього запускається трансформація в нормальну документоорієнтовану схему:

```bash
mongosh "$MONGO_URI" --file scripts/02_transform.js
```

Аналітичні запити запускаються окремими файлами:

```bash
mongosh "$MONGO_URI" --file queries/part2_queries.js
mongosh "$MONGO_URI" --file queries/part3_aggregations.js
mongosh "$MONGO_URI" --file queries/part4_indexes.js
```

Після тестового запуску в Atlas було:

```text
tracks_raw: 113999 документів
tracks:     113999 документів
```

## Як влаштована схема `tracks`

У CSV всі поля лежали на одному рівні: назва треку, артисти, жанр, tempo, energy, loudness та інші характеристики були просто колонками таблиці. Для MongoDB це не дуже зручно, бо частина полів логічно належить до одного об'єкта.

Тому в `scripts/02_transform.js` дані перетворюються так:

- `artists` стає масивом, бо один трек може мати кількох виконавців.
- аудіохарактеристики складаються у вкладений об'єкт `audio_features`.
- додається `duration_sec`, щоб мати тривалість у секундах.
- додається `popularity_tier`, щоб швидко бачити рівень популярності: `high`, `medium` або `low`.

Приклад документа після трансформації:

```json
{
  "track_id": "5SuOikwiRyPMVoIQDJUgSV",
  "track_name": "Comedy",
  "album_name": "Comedy",
  "explicit": false,
  "popularity": 73,
  "duration_ms": 230666,
  "track_genre": "acoustic",
  "artists": ["Gen Hoshino"],
  "audio_features": {
    "danceability": 0.676,
    "energy": 0.461,
    "loudness": -6.746,
    "speechiness": 0.143,
    "acousticness": 0.0322,
    "instrumentalness": 0.00000101,
    "liveness": 0.358,
    "valence": 0.715,
    "tempo": 87.917,
    "key": 1,
    "mode": 0,
    "time_signature": 4
  },
  "duration_sec": 230.7,
  "popularity_tier": "high"
}
```

Така структура краще підходить для запитів: наприклад, можна фільтрувати по `audio_features.tempo`, групувати по `track_genre`, або розгортати `artists`, коли треба рахувати статистику по кожному артисту окремо.

## Пояснення запитів

У частині 2 перший запит шукає треки для вечірки. Для цього я використав простий фільтр по трьох умовах: `danceability > 0.7`, `energy > 0.7`, а тривалість має бути від 3 до 5 хвилин, тобто `duration_ms` від `180000` до `300000`. У результаті виводяться назва треку, артисти, жанр, популярність, тривалість і дві основні аудіофічі, за якими відбирались треки. Результат відсортований за популярністю, щоб першими були найбільш відомі варіанти.

Другий запит шукає артистів, у яких є мінімум 3 треки, і всі ці треки мають популярність не нижче 60. Для цього масив `artists` спочатку розгортається через `$unwind`, потім треки групуються по артисту. Після групування ми вже можемо порахувати кількість треків, мінімальну популярність і середню популярність.

Третій запит шукає треки з незвично високим темпом для свого жанру. Логіка така: для кожного жанру рахується середній `tempo` і стандартне відхилення. Після цього трек вважається нетиповим, якщо його темп більший за `середнє + 2 * стандартне відхилення`. Тобто ми не просто шукаємо всі швидкі треки, а порівнюємо трек із типовим темпом саме його жанру.

Четвертий запит шукає музику для фонової роботи. Я використав умови з завдання: трек має бути тихим, майже без мовлення, переважно інструментальним і без explicit-контенту. Тому фільтр виглядає так: `loudness < -10`, `speechiness < 0.1`, `instrumentalness > 0.5`, `explicit = false`.

У частині 3 запити вже більше схожі на аналітичні звіти. Наприклад, топ артистів за середньою популярністю рахується тільки для тих, у кого є хоча б 5 треків. Це потрібно, щоб артист з одним випадково дуже популярним треком не займав перше місце.

Для настрою треків використано два поля: `valence` і `energy`. Якщо обидва високі, трек потрапляє в `happy`. Якщо енергія висока, але позитивність низька, це `angry`. Якщо позитивність висока, але енергія низька, це `calm`. Якщо обидва значення низькі, це `sad`. Після присвоєння настрою результат групується за двома полями одночасно: `track_genre` і `mood`. Так видно не тільки загальну кількість happy/angry/calm/sad треків, а й розподіл настроїв усередині кожного жанру.

Найбільш танцювальний жанр визначається за середнім `danceability`. Жанри з менш ніж 100 треками відсікаються, бо на маленькій кількості треків середнє значення може бути випадковим.

Після запуску найбільш танцювальним жанром вийшов:

```text
genre=kids
track_count=1000
avg_danceability=0.779
avg_energy=0.613
avg_valence=0.681
```

## Теоретичні відповіді

### Для чого потрібен `$unwind`

`$unwind` потрібен, коли в документі є масив, але для аналізу треба працювати з кожним елементом масиву окремо.

У цьому проєкті це найкраще видно на полі `artists`. Один трек може мати кількох артистів. Якщо групувати документи без `$unwind`, MongoDB буде сприймати весь масив артистів як одне значення. Це не підходить, коли треба порахувати статистику для кожного виконавця.

Після `$unwind: "$artists"` один документ із треком і трьома артистами тимчасово перетворюється на три документи: по одному на кожного артиста. Тоді `$group` може правильно порахувати кількість треків і середню популярність для кожного виконавця.

### Чим `$stdDevPop` відрізняється від `$stdDevSamp`

Обидва оператори рахують стандартне відхилення, тобто показують, наскільки сильно значення відхиляються від середнього.

`$stdDevPop` використовується, коли ми вважаємо наші дані повною сукупністю для аналізу. У задачі з темпом я аналізую всі треки кожного жанру, які є в датасеті, тому використовую саме `$stdDevPop`.

`$stdDevSamp` використовується для вибірки, коли наявні дані є лише частиною більшої сукупності. Він робить поправку на те, що ми бачимо не всі можливі дані.

Простіше кажучи: `$stdDevPop` - для всієї групи, `$stdDevSamp` - для вибірки з більшої групи.

### Що буде, якщо змінити поріг 5 треків для артистів

Якщо знизити поріг до 1, у топ можуть потрапити артисти з одним дуже популярним треком. Формально середня популярність буде високою, але такий результат не дуже надійний: один трек не показує стабільну популярність артиста.

Якщо підняти поріг до понад 50 треків, у результаті залишаться тільки артисти, яких у датасеті дуже багато. Такий рейтинг буде стабільнішим, але він може відкинути артистів, які справді популярні, просто мають менше треків у цьому датасеті.

Тому поріг 5 - це компроміс: ми вже відсікаємо випадкові одиничні треки, але ще не залишаємо тільки найбільших артистів.

### Що буде, якщо змінити поріг 100 треків для жанрів

Поріг 100 треків потрібен для статистичної надійності. Якщо в жанрі мало треків, один або два дуже танцювальні треки можуть сильно підняти середнє значення.

Якщо знизити поріг до 50, у розрахунок потрапить більше жанрів. Результат може змінитися, але довіра до нього буде трохи нижчою, бо середні значення для менших груп менш стабільні.

## Індекси та оптимізація

У частині 4 я порівнював запити до і після створення індексів через `explain("executionStats")`. Найважливіші поля там такі:

- `COLLSCAN` означає, що MongoDB переглядає всю колекцію.
- `IXSCAN` означає, що MongoDB використовує індекс.
- `totalDocsExamined` показує, скільки документів реально довелося прочитати.
- `totalKeysExamined` показує, скільки ключів індексу було переглянуто.
- `executionTimeMillis` показує час виконання в мілісекундах.

### Індекс для пошуку танцювальних pop-треків

Запит шукає pop-треки з `danceability >= 0.7` і сортує їх за популярністю:

```js
db.tracks.find({
  track_genre: "pop",
  "audio_features.danceability": { $gte: 0.7 }
}).sort({ popularity: -1 }).toArray();
```

Для нього створено індекс:

```js
{
  track_genre: 1,
  "audio_features.danceability": 1,
  popularity: -1
}
```

Поле `track_genre` стоїть першим, бо це точний пошук по жанру. Потім іде `danceability`, бо це умова діапазону. `popularity` додана в індекс, бо результат сортується за популярністю.

До індексу MongoDB прочитала всю колекцію:

```text
nReturned=354
totalDocsExamined=113999
totalKeysExamined=0
executionTimeMillis=90
plan=SORT -> COLLSCAN
```

Це означає, що база переглянула всі 113999 документів, знайшла 354 потрібні, а потім окремо відсортувала результат.

Після створення індексу:

```text
nReturned=354
totalDocsExamined=354
totalKeysExamined=354
executionTimeMillis=2
plan=FETCH -> SORT -> IXSCAN
indexName=idx_genre_danceability_popularity
```

Тут вже видно реальний ефект індексу: MongoDB переглянула тільки 354 ключі індексу і 354 документи замість 113999 документів. Час виконання зменшився з 90 мс до 2 мс.

### Індекс для музики для роботи

Другий індекс потрібен для частого пошуку фонової музики:

```js
{
  explicit: 1,
  "audio_features.instrumentalness": 1,
  "audio_features.speechiness": 1
}
```

`explicit` стоїть першим, бо це точна умова `false`. Далі йдуть числові аудіофічі, по яких використовуються умови діапазону.

До індексу:

```text
nReturned=16141
totalDocsExamined=113999
totalKeysExamined=0
executionTimeMillis=133
plan=COLLSCAN
```

MongoDB знову переглядала всю колекцію.

Після створення індексу:

```text
nReturned=16141
totalDocsExamined=16141
totalKeysExamined=16602
executionTimeMillis=40
plan=FETCH -> IXSCAN
indexName=idx_work_music
```

Після індексу база вже не читає всі 113999 документів. Вона проходить по індексу, знаходить відповідні ключі і читає тільки документи, які можуть підійти під запит. Час зменшився зі 133 мс до 40 мс.

### Covered query

У завданні був такий запит:

```js
db.tracks.find({
  track_genre: "pop",
  popularity: { $gte: 70 }
});
```

У такому вигляді це не covered query. Причина проста: запит без проєкції повертає повні документи. Індекс не містить усіх полів документа, тому MongoDB все одно повинна звертатися до самої колекції.

Щоб запит був covered, треба повертати тільки ті поля, які є в індексі, і вимкнути `_id`, бо `_id` повертається за замовчуванням:

```js
db.tracks.find(
  {
    track_genre: "pop",
    popularity: { $gte: 70 }
  },
  {
    _id: 0,
    track_genre: 1,
    popularity: 1
  }
);
```

Для такого варіанта `explain()` показав:

```text
winningPlan.stage=PROJECTION_COVERED
inputStage.stage=IXSCAN
indexName=idx_genre_danceability_popularity
nReturned=317
totalKeysExamined=620
totalDocsExamined=0
executionTimeMillis=1
```

Найважливіше тут - `totalDocsExamined=0`. Це означає, що MongoDB взяла всю потрібну інформацію прямо з індексу і не відкривала документи з колекції. Саме це і є covered query.

Для цього конкретного projected-запиту компактнішим був би індекс `{ track_genre: 1, popularity: 1 }`, але індекс із першого завдання також може його покрити, бо в ньому вже є і `track_genre`, і `popularity`.
